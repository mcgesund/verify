# McGesund Verify


Verifies a McGesund review **without McGesund**: signatures (Ed25519, ML-DSA-87, SLH-DSA), content, origin, keys, the timestamp proof in the Bitcoin blockchain and the entry in the public transparency log.

It works on a **verification package** (`mcgesund-verification-package-<id>.json`). The package is downloaded on mcgesund.eu (and the country sites such as mcgesund.at or mcgesund.ch) from the verification dialog of a review ("Verify authenticity" → "Download verification package") as soon as the review is anchored in Bitcoin.

This description is sufficient to re-implement the verification yourself, even without this tool.

## Quick start

Requirement: Node.js version 22 or later.

```bash
git clone https://github.com/mcgesund/verify.git
cd verify
npm install
curl -o mcgesund-keys.json https://mcgesund.eu/.well-known/mcgesund-keys.json
node bin/mc-verify.js mcgesund-verification-package-<id>.json --keys mcgesund-keys.json --online
```

The command is also available as `mc-verify` after `npm install -g .` (or `npm link`), e.g. `mc-verify mcgesund-verification-package-<id>.json --keys mcgesund-keys.json --online`.

| Option | Effect |
|---|---|
| `--keys <file>` | compares all keys against the public key directory and verifies their Bitcoin proof. Without it, signatures are only checked against the keys inside the package and the tool prints a warning: that does not prove who signed it |
| `--online` | verifies the review's Bitcoin proof against the blockchain (block header via the public Blockstream Esplora API — only the block height is sent, not the digest) and checks that every event of the review is contained in the signed transparency log (section 8) |
| `--server <url>` | McGesund website from which the transparency log and the key directory are fetched (default: `https://mcgesund.eu`) |
| `--log-proof <file>` | checks the review against a saved answer of the log API (`/api/transparenz/proof/<review-id>`) instead of fetching it — works offline, needs `--keys` |
| `--export-ots <folder>` | writes the envelope and proof as files for `ots verify` with your own Bitcoin node (section 10, level C) |
| `--log` | instead of a package, verifies the entire transparency log: signatures of all signed tree heads and their consistency with each other |
| `--full` | with `--log`: additionally downloads all entries, recomputes every leaf and builds the root itself |

Exit code: `0` = no errors, `1` = at least one error, `2` = file not readable.

### Demo files

Examples are in `examples/`: `demo-keys.json` (key directory), `package-unchanged.json` (an unmodified review), `package-redacted.json` (a redacted one), `package-in-log.json` with `log-proof.json` (a review with entries in the transparency log, including the server response). Tests run with `npm test`.

> The files in `examples/` are demo data signed with demo keys generated by `examples/generate.js` — they are not McGesund reviews and the demo keys are not in McGesund's key directory. Real verification packages are downloaded from a review's verification dialog.

```bash
node bin/mc-verify.js examples/package-unchanged.json --keys examples/demo-keys.json
node bin/mc-verify.js examples/package-in-log.json --keys examples/demo-keys.json --log-proof examples/log-proof.json
```

Leave out `--online` for the demo packages: their log entries exist only in `log-proof.json`, not on McGesund's server — check them with `--log-proof` as shown above. The demo's Bitcoin timestamps are real OpenTimestamps proofs; until Bitcoin has confirmed them the tool reports them as "not yet anchored". `node examples/update.js` fetches the confirmations from the calendars and fills in the block heights; `node examples/generate.js` creates a fresh set of demo files with new keys.

## Libraries used

Exclusively public libraries, independent of the signature implementation on the McGesund server:

| Purpose | Library |
|---|---|
| Ed25519 | Node.js (`node:crypto`) |
| ML-DSA-87, SLH-DSA-SHA2-256f | `@noble/post-quantum` |
| CBOR | `cbor-x` |
| OpenTimestamps | own minimal implementation in `lib/opentimestamps.js` (reading proofs, checking them against Bitcoin block headers); independent of the OpenTimestamps library used on the server |
| Bitcoin block headers (`--online`) | public [Blockstream Esplora](https://github.com/Blockstream/esplora) API at `https://blockstream.info/api` |

FN-DSA (Falcon) only appears in older origin stamps of QR codes. These stamps use a format from a preliminary draft of FIPS 206 and are not verified here; the tool reports a note (`NOTE`) for them, not an error (`ERROR`).

## 1. File structure

```json
{
  "type": "mcgesund-verification-package",
  "version": 1,
  "createdAt": "…",
  "comment": "<review id>",
  "envelope": "MCG1:…",
  "record": { … },
  "attestation": { … },
  "keyDirectory": "https://<domain>/.well-known/mcgesund-keys.json",
  "howToVerify": "…"
}
```

| Field | Content |
|---|---|
| `envelope` | Signed envelope of the review, exactly as it was created on submission |
| `record` | The displayed review: text, hearts, geo data, labels |
| `attestation.envelope` | Public Ed25519 key for the envelope |
| `attestation.stamps` | Public keys of the PQ signatures in the envelope, with the key's Bitcoin proof |
| `attestation.qr` | QR reviews only: envelope of the QR code and its PQ stamps (origin) |
| `attestation.commentAnchor` | Bitcoin proof of the review (OpenTimestamps, base64) with block height |
| `attestation.redaction` | Redacted reviews only: the redaction seal |

The package contains nothing secret: no coordinates, no contact details, no QR identifier.

## 2. Envelope

```
"MCG1:" + base64url( CBOR( envelope ) )      (base64url without padding)
```

| Version | CBOR array |
|---|---|
| v3 | `[3, payloadBytes, ed25519Sig]` |
| v4 | `[4, payloadBytes, ed25519Sig, [[algorithm, kid, sig], …]]` |

- All signatures apply to the **same** `payloadBytes`, i.e. the raw bytes, not the decoded content.
- `payloadBytes` is itself CBOR. The most important fields:

| Field | Meaning |
|---|---|
| `typ` | `rev-comment` = review, `rev-wall`/`rev-single`/`rev-event`/… = QR code, `rev-redaction` = redaction seal |
| `kid` | Key of the Ed25519 signature |
| `c` | ID of the review |
| `iat` | Time of signing (Unix seconds) |
| `rh`, `rv` | Hash of the record and version of the hash rule (section 3) |
| `h` | sha256 of the text (older reviews without `rh`) |
| `qh` | sha256 of the QR envelope the review originates from |
| `pv` | List of PQ algorithms that **must** be present in the envelope |

**Verification rules:**
1. The Ed25519 signature must be valid.
2. Every signature in the v4 list must be valid.
3. Every algorithm from `pv` must appear in the list. If one is missing, a signature has been removed: **error**.
4. A v3 envelope with a non-empty `pv` is an **error**.

**Algorithms:**

| Identifier | Algorithm | Standard |
|---|---|---|
| `ed` | Ed25519 | RFC 8032 |
| `ml-dsa-87` | ML-DSA-87 | FIPS 204 |
| `slh-dsa-256f` | SLH-DSA-SHA2-256f | FIPS 205 |
| `falcon-512`, `falcon-1024` | FN-DSA (Falcon), only in older stamps | FIPS 206 (draft) |

Keys and signatures are encoded raw (base64), not wrapped in ASN.1/DER. ML-DSA and SLH-DSA are used in their pure form (not the pre-hash variants) with an empty context string. Domain separation is done inside the signed payload: its `typ` field names the purpose (`rev-comment`, `rev-redaction`, `tlog-root`, …), and a verifier must check it.

## 3. Hash of the record (`rh`, rule version 1)

`rh` = sha256 (hex, lowercase) over the UTF-8 text of this JSON array, without whitespace (output of `JSON.stringify`):

```
[1, Content, AverageRating, ValueRating, ServiceRating, CleanlinessRating,
 QualityRating, productLabel, eventLabel, geoStatus, geoVerified,
 geoDistance, viaRotatingToken, qrEnvelopeHash]
```

| Field type | Fields | Normalization |
|---|---|---|
| Text | Content, productLabel, eventLabel, geoStatus, qrEnvelopeHash | empty string and missing → `null`, otherwise string |
| Decimal | AverageRating | number with exactly two decimal places as a **string**, e.g. `"4.50"`; missing → `null` |
| Integer | Value-/Service-/Cleanliness-/QualityRating, geoDistance | rounded to an integer; missing → `null` |
| Boolean | geoVerified, viaRotatingToken | `true` only for `true`, `1` or `"true"`, otherwise `false` |

`qrEnvelopeHash` = sha256 (hex) of the QR envelope from `attestation.qr.envelope`; `null` for reviews without a QR code.

**Deliberately not in the hash:** everything that may legitimately change after submission: the company's reply, moderation status, verification status, language of the flag.

**Verification rule:** The hash computed from `record` must match `rh` in the envelope. If it does not match, section 5 applies. If there is no redaction seal, this is an **error**.

## 4. Origin (QR reviews)

1. sha256 (hex) of `attestation.qr.envelope` must match the review's `qh`.
2. The Ed25519 signature of the QR envelope must be valid (key `kid` from its payload).
3. `attestation.qr.payloadHash` = sha256 (base64) of the `payloadBytes` of the QR envelope.
4. Every stamp in `attestation.qr.stamps` must be a valid signature over these `payloadBytes`.

## 5. Redacted reviews

If McGesund subsequently removes names from a review, the text no longer matches the signature made at submission. The original signature is nevertheless preserved unchanged. In addition, McGesund signs a **redaction seal** (`attestation.redaction.envelope`, type `rev-redaction`):

| Field | Meaning |
|---|---|
| `c` | ID of the review |
| `eh` | sha256 (hex) of the **original envelope** (`envelope` in the package) |
| `rh` / `h` | Hash of the redacted version, according to the same rule as section 3 |
| `iat` | Time of the redaction |

**Verification rules:**
1. The Ed25519 signature of the seal must be valid.
2. `c` must equal the review's `c`.
3. `eh` must equal the sha256 of `envelope`.
4. The hash computed from `record` must equal the seal's `rh`.

**What this proves and what it does not:**
- Proven: this version is the edit of exactly this submission that McGesund confirmed at this point in time. Any further change is detected.
- Not provable: what was there before. The original text is deliberately not included anywhere; otherwise the redacted names would be readable again.

## 6. Keys

Every key is listed in the public key directory with its algorithm, validity, revocation and its own Bitcoin proof. A key's proof applies to this value:

```
sha256( "kid:<kid>\nvariant:<algorithm>\npubkey:<publicKey>\nactiveFrom:<validFrom as ISO-8601 with milliseconds, UTC>" )
```

**Verification rules:**
1. The key in the package must match the key in the directory.
2. The Bitcoin proof must refer to exactly this value.
3. **Revoked keys:**
   - `superseded`: replaced as scheduled; all signatures remain valid.
   - `compromised`: A signature only counts if the review was anchored in Bitcoin **before** `revokedAt`.

## 7. Bitcoin proof of the review

`attestation.commentAnchor.otsProof` is an OpenTimestamps proof (base64).

**Verification rules:**
1. The proof must refer to the sha256 (hex) of the envelope, i.e. of the text `"MCG1:…"` itself.
2. The proof leads via a Merkle path to a Bitcoin transaction in the specified block.

The proof shows: exactly this signed envelope existed no later than the time of this block. This remains valid even if a signature algorithm is broken later, because only SHA-256 matters for it.

## 8. Transparency log

McGesund maintains a public log of all events concerning a review: submitted, published, not approved, removed, hidden, redacted. It contains **no text and no names**, only identifiers, hashes, the time and, for removals, a reason from a fixed list. This makes it possible to verify that McGesund does not silently remove or rewrite any review.

The log starts with its launch. Older reviews have no entries; they are not added retroactively. The API returns the date of the first entry as `logStart`.

### Entries

| `kind` | Meaning | Reason |
|---|---|---|
| `submitted` | submitted, awaiting approval | – |
| `submitted_published` | submitted and published immediately | – |
| `published` | published (approval or visible again) | – |
| `rejected` | not approved | required |
| `removed` | removed after publication | required |
| `hidden` | hidden automatically | required |
| `redacted` | redacted (section 5) | required |
| `imported_published` | existed before the log started, publicly visible when taken over; names the redaction seal if redacted | – |
| `imported` | existed before the log started, not public when taken over (pending, rejected, removed or hidden — the reason follows as a separate entry) | – |

Reviews submitted before the log started were taken over once with their state at that time. The entry is dated to the takeover, not to the submission; the submission time is proven by the review's own Bitcoin proof (section 7).

Reasons (`category`):

| Identifier | Meaning | set by |
|---|---|---|
| `insult` | Insult | moderation |
| `off_topic` | Off-topic (e.g. politics, advertising) | moderation |
| `personal_data` | Personal data | moderation |
| `fake_or_spam` | Fake or spam | moderation |
| `no_customer_contact` | No customer contact | moderation |
| `author_request` | At the author's request | moderation |
| `legal_order` | Court or official order | moderation |
| `policy_violation` | Violation of the guidelines | moderation |
| `provider_deleted` | Provider deleted | system |
| `invalid_signature` | Signature verification failed | system |
| `not_recorded` | Not recorded before the log started (taken-over reviews only) | system |

An entry has the fields `kind`, `at` (ISO-8601 with milliseconds, UTC), `category`, `commentDocumentId`, `firmaDocumentId`, `envelopeHash` (sha256 hex of the review's envelope), `sealHash` (sha256 hex of the redaction seal, only for `redacted`) and `salt` (16 random bytes, hex).

**Canonical entry data** (version 1): JSON array without whitespace, in exactly this order, missing values as `null`:

```
[1, kind, at, category, commentDocumentId, firmaDocumentId, envelopeHash, sealHash, salt]
```

### Merkle tree

According to RFC 9162 (Certificate Transparency 2.0), section 2.1:

```
leaf = sha256(0x00 ‖ UTF-8(canonical entry data))
node = sha256(0x01 ‖ left ‖ right)
```

With n leaves, the tree splits at the largest power of two k < n: root = node(root(leaves 0..k-1), root(leaves k..n-1)). Inclusion and consistency proofs are verified according to RFC 9162, sections 2.1.3 and 2.1.4.

### Signed tree head

Every hour, provided new entries have been added, McGesund signs a tree head: a v4 envelope (section 2) with the payload

```
{ v: 1, typ: "tlog-root", n: tree size, r: root (hex), iat, kid, pv: ["ml-dsa-87"] }
```

signed with Ed25519 and ML-DSA-87. The sha256 (hex) of the envelope text is anchored in Bitcoin via OpenTimestamps (as in section 7). The tree head proves: no later than this block, the log contained exactly these entries in exactly this order.

### Erasure request

Upon an erasure request (Art. 17 GDPR, e.g. when a provider is deleted), the identifiers, hashes and `salt` of an entry are cleared. The leaf remains and all proofs remain correct. Without `salt`, the leaf can no longer be linked to any envelope, not even with the envelope in hand. The API shows cleared entries with `erased: true`.

### API

At `https://mcgesund.eu`:

| Request | Content |
|---|---|
| `GET /api/transparenz/roots?limit=20` | signed tree heads, newest first, with Bitcoin proof |
| `GET /api/transparenz/entries?from=0&limit=100` | entries starting at a position (0-based, at most 500) |
| `GET /api/transparenz/proof/<review-id>` | entries of a review with inclusion proof against the newest tree head, plus `pending` (entries after this tree head) and `logStart` |
| `GET /api/transparenz/consistency?from=m&to=n` | consistency proof between the tree heads of sizes m and n |
| `GET /.well-known/mcgesund-keys.json` | key directory |

Rate limit: 120 requests per minute per IP address. Beyond that, the server responds with `429` and states in `Retry-After` how many seconds to wait.

### Verification rules

For a review (verification package, field `comment`):

1. The tree head is validly signed with Ed25519 and ML-DSA-87; the keys are listed in the key directory and were not revoked at the time of signing. `n` and `r` in the payload match the tree size and root.
2. Every leaf results from the fields of its entry (canonical entry data).
3. The inclusion proof leads from the leaf to the root of the tree head.
4. `envelopeHash` is the sha256 of the envelope in the verification package.
5. If the review is redacted, the last `redacted` entry names in `sealHash` exactly the seal in the verification package.
6. If the review is publicly visible, the last entry must not be `removed`, `rejected` or `hidden` (unless further entries follow, `pending` > 0).
7. The Bitcoin proof of the tree head refers to the sha256 of its envelope.

For the entire log:

8. Every tree head is a continuation of the previous one (consistency proof). If this fails, entries have been removed or rewritten.
9. Anyone who downloads all entries, recomputes every non-cleared leaf and builds the root themselves must obtain the root of the newest tree head.

Anyone who saves tree heads at intervals can prove at any time that nothing from the past has disappeared later: the consistency proof between the saved and the current tree head must hold.

## 9. Result

| Result | Meaning |
|---|---|
| `Result: no errors` (with `--keys`) | The review was submitted via McGesund in this form, is unchanged or only verifiably redacted, and existed at the stated point in time. With `--online` additionally: every event of the review is contained in the signed transparency log |
| `ERROR` (at least one; summary e.g. `Result: 1 error, 2 notes`) | at least one check has been recomputed and found to be wrong: the review has been modified or the package is incomplete |
| `NOTE` | something could not be verified, e.g. key directory not specified, proof only verified offline. This is not a finding of forgery |

## 10. Guide for verifiers

Three levels, depending on whom the verifier wants to trust. Each level includes the previous one.

| Level | Trusted | Effort |
|---|---|---|
| A: Verification dialog on the website | the browser and the verification page served by McGesund | none |
| B: Verification tool | the open-source tool and a public block explorer | a few minutes |
| C: Own Bitcoin node | nobody except SHA-256 and the Bitcoin blockchain | about one day (one-time, synchronization) |

### Level A: Verification dialog

1. On the review, click "Verify authenticity". The browser recomputes all signatures itself.
2. As soon as the review is anchored in Bitcoin (usually 1–2 hours after submission): "Download verification package". The file is named `mcgesund-verification-package-<id>.json`.
3. Keep the verification package. It remains verifiable even if the review is later no longer online.

### Level B: Verification tool

Requirement: Node.js version 22 or later.

1. Get this tool and install the dependencies: `npm install` in the tool's folder.
2. Save the key directory as of the time of verification:
   ```bash
   curl -o mcgesund-keys.json https://mcgesund.eu/.well-known/mcgesund-keys.json
   ```
   The directory is identical on all McGesund websites (e.g. `mcgesund.eu`, `mcgesund.at`, `mcgesund.ch`). Whether a key is genuine does not depend on the domain but on its own Bitcoin proof (section 6).
3. Verify:
   ```bash
   node bin/mc-verify.js mcgesund-verification-package-<id>.json --keys mcgesund-keys.json --online
   ```
4. Read the result (section 9). With `Result: no errors`, the review is genuine, unchanged or verifiably redacted, and it existed no later than the stated Bitcoin block.
5. Optionally verify the entire transparency log (section 8): all signed tree heads, whether each one is a continuation of the previous one, and with `--full` every entry:
   ```bash
   node bin/mc-verify.js --log --full --keys mcgesund-keys.json --online
   ```
   Anyone who keeps the output with its date can later prove that nothing has disappeared from the log since then.

### Level C: Own Bitcoin node

This also removes the need to trust the block explorer.

1. **Install Bitcoin Core** (bitcoincore.org; on macOS also `brew install bitcoin`).
2. **Configure to save space.** Add to the file `bitcoin.conf`:
   ```
   prune=10000
   server=1
   ```
   Location: macOS `~/Library/Application Support/Bitcoin/`, Linux `~/.bitcoin/`, Windows `%APPDATA%\Bitcoin\`.
   With `prune`, about 10 GB is sufficient. For verification, the block headers are enough, and a pruned node keeps them as well.
3. **Start the node** (`bitcoind`) and let it synchronize completely. Progress: `bitcoin-cli getblockchaininfo` (field `verificationprogress` close to 1).
4. **Install the OpenTimestamps client:**
   ```bash
   pip install opentimestamps-client
   ```
5. **Extract the envelope and proof from the verification package**, either with this tool:
   ```bash
   node bin/mc-verify.js mcgesund-verification-package-<id>.json --export-ots ots/
   ```
   or without the tool using `jq`:
   ```bash
   jq -j .envelope mcgesund-verification-package-<id>.json > envelope.txt
   jq -r .attestation.commentAnchor.otsProof mcgesund-verification-package-<id>.json | base64 -d > proof.ots
   ```
   Important: `envelope.txt` must contain exactly the envelope, **without a trailing newline** (`jq -j`). An additional character changes the hash, and the verification fails.
6. **Verify:**
   ```bash
   ots verify -f envelope.txt proof.ots
   ```
   Expected output: `Success! Bitcoin block <height> attests existence as of <date>`. The block height must match `attestation.commentAnchor.btcBlock`.
7. **Verify the keys the same way** (optional): For each key from the key directory, write the text from section 6 to a file without a trailing newline, base64-decode `anchor.otsProof` and also verify it with `ots verify -f`.

Level C does not verify the signatures themselves (sections 2 to 5). For that, level B or your own implementation according to this specification is still required.

### What a verifier should record

- Verification package and key directory as files, with the date of retrieval
- Output of the verification tool or of `ots verify`
- Version of the verification tool used
